# UI・ドキュメントの関係に合う情報設計

## 元資料から読み取り作業へ

最初に、その利用者が画面から答えたい問いを少数置く。例は「どの領域に属するか」「条件を満たす候補はどれか」「今はどの状態か」「この項目をAIへどう指定するか」。元資料と照合しながら、必要な情報と関係を選ぶ。架空例の構成を別の画面へそのまま適用しない。

ドキュメントでは、読者が理解したい内容に合わせて、見出し・段落・箇条書き・表などを選ぶ。UIの比較・操作・状態確認は、その用途がある場合に使う。

親子・同列・依存・順序と、重要度は別の関係である。名称の似方、データの列順、入れ子の実装だけで利用者向けの階層・優先順位を確定しない。仕様や実物に根拠がない場合は同列に留める、関係未確認と示すなど、断定を避ける。

## 一文に詰め込まれた役割を表し分ける

例えば `A画面 / Bコンポーネント: 成功` がボタン・選択肢・説明になっている場合、所属、対象、状態、操作を元資料から確かめる。「A画面にBコンポーネントが属する」は親子関係、「成功」は対象の状態であり、状態を子項目として階層の続きを作らない。どの対象が成功したか不明なら、Bの状態と決めつけない。

成功がBの状態と確認できた場合の表現例：

```text
A画面
  Bコンポーネント    ［成功］
```

親の文脈は見出しや包含、対象名は項目の名前、状態は対象に対応する状態表示で伝える。ボタンは実際の操作に合うラベルを選ぶ。選択肢は所属が分かるまとまりや周辺の文脈を使い、同名対象を選び分けられる情報を保つ。表示と支援技術に渡る関係も揃える。

文章と同じ情報を別の説明カードへ繰り返すだけでは、関係の改善にならない。各コンポーネントの役割を確かめ、必要な説明・条件・識別情報を残して、構造で伝えられる反復を整理する。パスや短い併記が用途に合う場合もあり、スラッシュ・一文という形式だけで修正を決めない。常に見出しやバッジへ分割することも求めない。

UI・説明HTML・可視化で、見出しや配置だけで対象と用途が分かるなら、それを言い直す補助ラベルや導入文を省く。例えば「配送先」という見出しの下に住所欄があるとき、「配送先情報」「ここでは配送先を設定できます」が新しい意味を持つか確かめる。一方、住所欄の名前や「海外への配送はできません」という条件は別の役割を持つ。説明を減らすためにこれらを消したり、根拠のない階層を作ったりしない。可視ラベルや見出しを整理するときも、アクセシブルな名前と意味構造を保つ。ラベルや説明の一律禁止ではなく、残る表示と構造で必要な意味を読めるかで判断する。

## 表現の選び方

| 伝えたい関係 | 候補となる表現 | 確認点 |
| --- | --- | --- |
| 全体と部分、所属 | 見出し、包含、入れ子のリスト、領域分け | 親と子、同列の項目が分かるか |
| 対象と状態 | 対象に近接した状態表示、対応が分かる整列 | 誰の状態か分かり、状態を子対象や操作として扱っていないか |
| 同じ観点での比較 | 行・列を揃えた表、整列した比較欄 | 単位・条件・不明値を同じ位置で比較できるか |
| 順序のある実施 | 番号付き手順、段階表示 | 前提、現在位置、次、完了条件が分かるか |
| 依存、分岐、接続 | 接続図、隣接した説明、依存一覧 | 線や方向に定義があり、意味構造でも関係を読めるか |
| 重要度、注意、補足 | 配置、文字の強弱、余白、注記 | 強調に根拠があり、同階層・同意味で一貫しているか |

見出し、近接、余白、整列、文字サイズ・太さを、伝える関係のために使う。全情報を同じカードに入れることや、画面全体を一律に図解することを既定にしない。説明文が多いなら、何を関係として表せるか検討する。ただし必要な条件、例外、判断根拠を短文化や折りたたみで失わせない。折りたたむ場合も、判断前に気づいて到達できる位置に手掛かりを残す。

## 比較する画面

必須条件と好みを分ける。まず必須条件を満たす候補があるかを確認し、その後、有効な候補間で好みや利点を比較する。「条件を満たす」と「最も好ましい」を同一視しない。不明な条件は合格として扱わない。除外理由と、値の条件・単位・期間を保持する。仕様に順位や推薦の根拠がなければ勝手に一番を決めない。

## 操作する画面

現在の状態、操作対象、次にできる操作、適用条件、実際に起きる結果をつなげる。確認画面への移動と確定処理、ローカルの変更と保存済み状態、送信の試行と成功を区別する。必要なエラー、空、処理中、成功状態を、実際の振る舞いに合わせて扱う。説明HTMLに操作がなければ操作機能を足さない。

## 人の理解から元の対象へ戻る

人向けの名称は、意味や役割を分かるようにする。原表現は、その利用者の作業に必要な場所で対応づける。表の識別列、補足、詳細欄、選択対象の参照表示などから選び、コピー機能・チャット・自動送信は必須にしない。

例えば、架空の仕様で「東拠点の共有先」と「西拠点の共有先」が両方 `標準` という表示名を持つなら、所属と確認済みIDを対応させる。「西拠点の標準、共有先ID `dst-west` の保持期間を変更したい」のように、画面で理解した対象・意図と元の対象が一致するか確かめる。表示名だけや行番号だけでは一意にならない場合がある。

未定義の状態値 `paused_v2` があっても「一時停止」と意味を補わない。「状態の意味は未確認（原値 `paused_v2`）」など、分かる事実と不明点を分ける。長いID・パスでも重要な区別が省略されない表示や確認手段を選ぶ。
