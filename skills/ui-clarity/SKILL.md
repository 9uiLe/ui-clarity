# UI Clarity

AIが作成・編集する成果物に含まれる日本語と、その意味の伝え方を扱う。意味を保ち、読者と用途に必要な内容・関係・違いを理解できる表現に整える。UIや説明資料では、元のコードやデータを事前に読んでいない読者も想定する。会話の返答や進捗報告など、対話そのものの文体調整には適用しない。文章量、図、カード、装飾の数を成果にしない。

| 成果物 | 日本語が果たす役割 |
| --- | --- |
| UI：HTML・アプリ・可視化 | 対象・所属・状態・操作を伝え、必要な理解・比較・操作を支える。説明・共有用HTMLと操作するUIを同じ優先度で扱う |
| ドキュメント | 読者に必要な内容・条件・根拠を、用語・説明順・見出しやまとまりで伝える |
| コードコメント | 対応するコードの条件・前提・意図を正確に伝える |

## 目的と範囲を決める

依頼と既存資料から、成果物、読者、利用場面、理解・判断・操作したいこと、変更できる範囲を確認する。技術者も読者に含める。完成条件と確認方法を短く置き、関係する仕事だけ選ぶ。コードコメントにUIの状態設計を課すなど、別の成果物の作業を持ち込まない。毎回の全面改修や、全参照資料の通読は不要。

| 依頼 | 行う仕事 | 境界 |
| --- | --- | --- |
| 作成・全体改善 | 根拠との照合、用途に合う日本語・構造、代表作業の確認。UIでは必要なスタイルや処理も許可範囲で扱う | 用途に不要な機能や説明を追加しない |
| レビューのみ | 実物と仕様を照合し、問題の場所・影響・根拠・改善案を返す | ファイルを変更しない。指摘なしも許容する |
| 文言だけの編集 | 意味・条件・用語を照合し、対象の日本語だけを編集。UIでは表示と対応する支援技術向け文言も整合させる | 構造・CSS・処理は変更しない。必要な構造改善は分けて提案する |

既存の用語集・文体・対象読者を優先する。読者の指定がなければ、UI・一般向けの説明資料は一般利用者、コードコメントはコードの保守者を仮読者とし、簡潔で中立的な文体を使う。専門文書は内容・周辺資料から読者を確かめる。仮定は短く伝える。既に適切な日本語は好みだけで変えない。

重大な未解決事項は、仕様・実装・実データなど調べられる事実を先に調べる。人の判断が必要なものだけ優先順に3つ以内で質問し、回答に依存しない作業は進める。軽微な仮定は明示して進める。資料と表示の矛盾は黙って解消せず報告する。

## 意味と参照の根拠を揃える

記述の意味・役割・条件を、定義、仕様、実装、実データなど、その成果物の根拠と照合する。UIでは対象の所属・状態・操作も確認する。名前から機能や優先順位を推測しない。根拠が不足する関係や値は未確認として扱い、未知の値を既知の状態に割り当てない。

読者に必要な意味を説明し、理解・比較・AIへの指示に原名称・識別子・パス・値が必要な場合は対応づける。原表現を一律に隠したり、全項目へ併記したりしない。同名の別対象や異なる状態は、所属・場所・識別子など必要な範囲で区別する。画面を基にAIへ指示する用途では、選んだ対象と渡す参照情報の一致を確かめる。存在未確認の参照先を作らない。

## 必要な表現を選び、作る・直す・指摘する

- 対象の日本語を作る・変える・レビューするときは [日本語と意味の保護](references/japanese-and-semantics.md) の共通項と該当する成果物の項目を読む。
- UIやドキュメントで関係、まとまり、包含、順序、比較、依存を扱うときは [情報設計](references/information-design.md) を読む。UI全体の改善では最初に参照する。
- 確認範囲・方法・完了判断は [検証](references/verification.md) から必要な項目を選ぶ。単純な文言修正に実画面の全状態試験を課さない。

UI（説明・共有用HTML、可視化を含む）では、日本語に詰め込まれた対象・所属・状態・操作を区別し、まず見出し、配置、包含、整列、近接、状態表示などで関係を伝える。それらで既に伝わる内容を言い直す補助ラベルや導入文を惰性で足さない。役割の異なる見出し・対象名・状態・操作や、必要な説明・条件・識別情報は残す。文言だけの依頼では、構造の改善は別提案にする。

UIの表示文言だけでなく、支援技術が受け取る名前・説明・関係も確認する。文字の表示ラベルがある操作では、その文字をアクセシブルな名前にも原則含める。記号だけの操作には機能を表す名前を用意する。名前の取得元を調べ、全要素へ一律に `aria-label` を付けない。

UIや構造を持つ文書では、見出し・表・フォームなどの意味構造と視覚的な関係・順序を揃え、対象環境の仕組みを使う。読み上げと操作順序も整合させる。色だけに意味を担わせない。

## 確認して返す

完成条件に必要な読解・代表作業を実物で確かめる。UIでは全体像が分かるだけで、必要な比較や操作ができないものを完成としない。比較・操作・AIへの対象指定が不要な成果物へ、それらを足す必要はない。

作成・変更したもの、目的、確認した条件と結果、未確認のことを短く説明する。静的検査、画面での実操作、人による理解の確認、実際の読み上げを区別し、未実施を確認済みにしない。

下書き・実装・ローカル検証は依頼範囲で進める。公開、push、PR作成、送信、削除、費用の発生、稼働中の環境変更は、具体的な対象と内容を示して実行前に確認する。
