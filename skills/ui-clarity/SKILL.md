# UI Clarity

説明・共有用HTMLと操作するUIを同じ優先度で扱う。元のコードやデータを事前に読んでいない利用者が、全体・親子・同列・重要度を理解し、必要な比較・操作を進め、必要ならAIに対象と意図を正確に伝えられることを成果とする。文章量、図、カード、装飾の数を成果にしない。

## 目的と範囲を決める

依頼と既存資料から、利用者、場面、理解・判断・操作したいこと、変更できる範囲を確認する。技術者も利用者に含める。完成条件と確認方法を短く置き、関係する仕事だけ選ぶ。毎回の全面改修や、全参照資料の通読は不要。

| 依頼 | 行う仕事 | 境界 |
| --- | --- | --- |
| 作成・全体改善 | 元資料との照合、表現の選択、文言・意味構造・必要なスタイルや処理、代表作業の確認 | 不要な比較機能や操作、組み込みチャット等を追加しない |
| レビューのみ | 実物と仕様を照合し、問題の場所・影響・根拠・改善案を返す | ファイルを変更しない。指摘なしも許容する |
| 文言だけの編集 | 対象・動作・状態・条件を照合し、必要な表示文言と対応する支援技術向け文言を編集 | 構造・CSS・処理は変更しない。必要な構造改善は分けて提案する |

既存の用語集・文体・対象読者を優先する。指定がなければ「一般利用者向けの簡潔で中立的な文体」を仮置きし、その仮定を短く伝える。既に適切な文言は好みだけで変えない。

重大な未解決事項は、仕様・実装・実データなど調べられる事実を先に調べる。人の判断が必要なものだけ優先順に3つ以内で質問し、回答に依存しない作業は進める。軽微な仮定は明示して進める。資料と表示の矛盾は黙って解消せず報告する。

## 意味と参照の根拠を揃える

対象の意味・役割・状態・関係を、定義、仕様、実装、実データと照合する。名前から機能や優先順位を推測しない。根拠が不足する関係や値は未確認として扱い、未知の値を既知の状態に割り当てない。

利用者に必要な意味を説明し、理解・比較・AIへの指示に必要な原名称・識別子・パス・値を対応づける。原表現を一律に隠したり、全項目へ併記したりしない。同名の別対象や異なる状態は、所属・場所・識別子など必要な範囲で区別する。画面で選んだ対象と、AIに渡す参照情報の一致を確かめる。存在未確認の参照先を作らない。

## 必要な表現を選び、作る・直す・指摘する

- 関係、まとまり、包含、順序、比較、依存を扱うときは [情報設計](references/information-design.md) を読む。全体改善では最初に参照する。
- 表示文言を作る・変える・レビューするときは [日本語文言と意味の保護](references/japanese-and-semantics.md) を読む。
- 確認範囲・方法・完了判断は [検証](references/verification.md) から必要な項目を選ぶ。単純な文言修正に実画面の全状態試験を課さない。

表示文言だけでなく、支援技術が受け取る名前・説明・関係も確認する。文字の表示ラベルがある操作では、その文字をアクセシブルな名前にも原則含める。記号だけの操作には機能を表す名前を用意する。名前の取得元を調べ、全要素へ一律に `aria-label` を付けない。

Webでは見出し・表・フォームなどの意味構造と視覚的な関係・順序を揃え、ネイティブでは対象環境の仕組みを使う。読み上げと操作順序も整合させる。色だけに意味を担わせない。

## 確認して返す

完成条件に必要な代表作業を実物で確かめる。全体像が分かるだけで、必要な比較や操作ができないものを完成としない。比較・操作が不要な画面へそれらを足す必要はない。

作成・変更したもの、目的、確認した条件と結果、未確認のことを短く説明する。静的検査、画面での実操作、人による理解の確認、実際の読み上げを区別し、未実施を確認済みにしない。

下書き・実装・ローカル検証は依頼範囲で進める。公開、push、PR作成、送信、削除、費用の発生、稼働中の環境変更は、具体的な対象と内容を示して実行前に確認する。
