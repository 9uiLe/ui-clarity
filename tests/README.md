# UI Clarity の検証

架空題材から実際の依頼を実行し、スキルの挙動を試す。初版の配信先の4依頼、所属・対象・状態・操作およびUI以外の日本語を扱う追加3依頼、業務情報の階層を扱う2依頼、補助ラベルと説明の役割を扱う1依頼を用意している。変更に関係する依頼を選び、スキルを利用するたびに実行する工程にはしない。

## 自動検証

Python 3.13 の Linux CI と、Python 3.14 の macOS arm64 で固定ハッシュのwheelを利用できる。その他の環境ではソース配布を使える。

リポジトリのルートから実行する。検証環境はプロジェクト外に作る。

```sh
python3 -m venv /tmp/ui-clarity-test-env
/tmp/ui-clarity-test-env/bin/python -m pip install --require-hashes -r tests/requirements.txt
PYTHONDONTWRITEBYTECODE=1 /tmp/ui-clarity-test-env/bin/python -m unittest discover -s tests -p 'test_*.py' -v
/tmp/ui-clarity-test-env/bin/python tests/check_repository.py
```

検査はGitの追跡ファイル（ステージ済みを含む）を対象とする。配布前に、無視されていない未追跡ファイルも含めて確認するときは `tests/check_repository.py --include-untracked` を使う。ローカルの開発支援設定や実行記録は配布しない。

CIでは配布物の単一入口、frontmatter、相対リンク、参照解決、公開対象へ混ざるローカル記録・秘密ファイルを検査し、その検査が壊れた入力を拒否することも試す。Markdownリンクの検査対象はインラインリンク・画像・参照定義で、アンカーの存在、HTML内のURL、完全なCommonMark解釈までは保証しない。ワークフローのmaster限定・読み取り権限・ActionのSHA固定も回帰検査する。別ジョブのGitleaksは、Gitの全取得履歴を走査する。

これらは、モデルの文言・情報設計の品質や意味保持の自動評価ではない。意図的な問題を含む `fixtures/*.html` を完成画面として合否判定しない。スキルの実質的な変更では、以下の該当する依頼による行動検証を別途行う。

## 導入コマンドの確認

READMEの導入・更新はVercel Skills CLIへ委ねます。CLIの変更時は公式仕様を照合し、公開リポジトリの`ui-clarity`検出と、プロジェクト外の一時ディレクトリへの導入・再導入を確認します。個人用配置先を変更しないため、試験では`--global`を外し、作業場所をその一時ディレクトリへ限定します。

```sh
DISABLE_TELEMETRY=1 pnpm dlx skills add 9uiLe/ui-clarity --skill ui-clarity --agent codex claude-code --yes
```

スキル本文・参照資料の一致と、Claude Code側のリンク先を確認します。`HOME`・`CODEX_HOME`は変更しません。実際の個人用導入・ツール内の認識・GitHub CIとは区別して結果へ記録します。これは外部CLIとの導入互換性の確認であり、CIにネットワーク依存の導入試験を追加するものではありません。

## pre-commitのサイズ検査

有効化は[README](../README.md#開発時のコミット検査)を参照。hookはPython 3の標準ライブラリとGitだけで動きます。既存の単体テスト実行コマンドで、hookの行動テストも実行されます。

検査対象はindexで追加・変更・改名などがステージされた通常ファイルです。差分の行数ではなく、ステージされたファイル全体のblobサイズを使い、20,000バイトを超えると拒否します。ちょうど20,000バイトは許可します。未追跡・未ステージ・変更のない追跡ファイル、削除、シンボリックリンク、submoduleは検査対象にしません。検査はファイルやindexを変更しません。

Gitの履歴やファイルの内容から作者を確実に判定できないため、通常のファイルは既定で対象にします。lockfileはhook内の名前一覧（例：`package-lock.json`、`pnpm-lock.yaml`、`uv.lock`、`Cargo.lock`）で除外します。手書きのJSONや`requirements.txt`を拡張子だけで除外することはありません。作者や生成元が既知のファイルは、必要に応じて`.gitattributes`へ明示します。

```gitattributes
generated/** linguist-generated=true
vendor/** linguist-vendored=true
docs/human-maintained.md agent-authored=false
generated/hand-written-wrapper.py agent-authored=true
```

これは指定方法の例です。このリポジトリには除外設定を追加していません。`agent-authored`のfalse／unset（`-agent-authored`も同じ）は対象外、true／set（値のない`agent-authored`も同じ）は強制検査です。強制検査はlockfileや生成物の除外より優先します。それ以外は、`linguist-generated`／`linguist-vendored`がtrue／setなら除外します。不明な値は除外の根拠にしません。生成物らしい名前・ディレクトリ・コメントだけでは自動判定しません。

`.gitattributes`はステージされた版を使い、Git標準のローカル属性（`.git/info/attributes`）やグローバル属性も反映します（[Gitの`--cached`仕様](https://git-scm.com/docs/git-check-attr)）。共有する除外指定は`.gitattributes`へ書き、そのファイルも`git add`してください。超過エラーの後は、コードを責務別のモジュール、テストを機能別、長い文書を見出し単位の参照資料へ分け、import・リンクと動作を確認して再ステージします。作業中のファイルを短くするだけではindexは更新されません。

## 再実行

1. 隔離したローカル作業場所を4つ用意し、それぞれに `fixtures/source.md` を置く。レビュー用には `review.html`、文言用には `copy-only.html` も置く。元フィクスチャは編集しない。
2. 各実行者へ、`skills/ui-clarity/SKILL.md`、必要な元ファイルと、`fixtures/requests.md` の該当依頼だけを渡す。期待結果、過去の採点、他の実行結果は渡さない。外部操作はせず、生成物と報告は隔離先へ保存する。別文脈を使えなければ自己検証と記録する。
3. 実行後、別の評価者が以下の基準で、出力・差分・実画面を確認する。生成物があるだけで合格にしない。

追加の3依頼は、`fixtures/requests.md` の該当依頼を使う。`roles-ui` と `roles-copy` は、それぞれ別の隔離先へ `roles-source.md`・`roles-ui.html` を置く。`artifact-japanese` は別の隔離先へ `artifact-japanese.md`・`artifact-comments.py` を置く。初版と同じく、実行者には元資料と依頼だけを渡す。

業務情報の2依頼は、別々の隔離先へ `business-hierarchy-source.md`・`business-hierarchy-data.json` を置き、`business-explain`・`business-operate` を実行する。画面・コンポーネントを親子の題材にせず、顧客・契約・請求書・明細という情報の関係を使う。スキルは試験のために先に変更せず、試験時の版を記録する。

`invoice-notification` は、別の隔離先へ `invoice-notification-source.md`・`invoice-notification.html` を置いて実行する。実行者にはスキル・この元資料とHTML・該当依頼だけを渡し、以下の判定基準は渡さない。

## 事前の判定基準

| ケース | 確認する成果 |
| --- | --- |
| 説明HTML | 営業資料の共有→領域→配信先の所属と同列が分かる。40 MB・社内のみ・30日以上・選択可能の必須条件で探し、国内・海外の「標準」を比較できる。好みの保持期間と合否を混ぜない。操作UIを無用に足さない |
| 操作UI | 同名の2対象を区別して選び、確認から確定、成功または成否不明の結果へ進める。選択と表示・処理のIDが一致する。確認時点で完了を表示しない。根拠のない再試行案内をしない |
| レビューのみ | 入力がバイト単位で同一。平坦な関係、同名の混同、未定義状態、条件を満たさない推薦、誤った完了文言、根拠のないエラー説明等を、場所・根拠・影響とともに指摘する |
| 文言のみ | HTML構造・CSS・処理を変えず、実態に合う文言へ修正。24時間前と承認待ちの例外、約5分、識別子・キー・関連・値・URL・イベント・補間変数・書式指定子・複数形構造を保持。共有キーの別用途を調べる。構造上の不足は別提案にする |

追加3依頼の基準：

| ケース | 確認する成果 |
| --- | --- |
| 役割を表し分けるUI改善 | A／D画面の所属、同列のB／C、誰の成功・確認中か、詳細を表示する操作を読み取り分けられる。状態を子対象へ階層化せず、説明の反復を増やさない。選択と詳細の対応を保つ |
| 同じUIの文言のみ | タグ・属性・CSS・処理・値を保ち、ボタンの実際の動作などを文言で整える。構造改善は別提案とする |
| 文書・コメント | READMEの最大3回・認証エラーの例外・約5秒を保つ。コメントは実装の条件・参照・値・型検査用指示・実行コードを保持し、UI専用の作業を追加しない |

UIの追加依頼では、仕様に合う短いパンくずを表記だけで問題認定しないこと、`P画面 / Qコンポーネント: 完了` の状態対象を推測しないことも確認する。通常の会話はスキルの対象外であり、成果物の修正と作業報告の文体調整を同じ必須工程にしない。

`invoice-notification` では、見出し・配置・包含などで既に伝わることを反復する「通知設定」「ここではメール通知を設定できます」等を整理し、同じ意味の説明カードへ置き換えていないか確認する。見出しとフォーム名など役割が異なる文字列の重なりは、それだけで問題にしない。送信先が請求担当者であること、オンでは初回発行時だけ送ること、再発行時は送らずオフでは初回も送らないことを、設定判断の前に読めるか照合する。文字数・カード数・特定の文言やレイアウトは合格条件にしない。

同ケースは初期オン→オフ→オンと初期状態へ戻す操作を実物で試し、表示とcheckboxの値、可視の名前とアクセシブルな名前・説明、読み順・操作順を確認する。ローカルの変更を保存済み・送信済みと表示せず、実送信や永続保存を足さないことも確かめる。既存の文言のみ・レビューのみの依頼は引き続き別に評価し、この全体改善ケースの結果から編集範囲を守る能力まで確認済みにしない。

業務情報の2依頼では、顧客→契約→請求書→明細の親子と同列が読み取れるか、請求書の入金状態を契約・明細へ誤って帰属させていないか、問い合わせの参照関係を請求明細の包含と混同していないかを確認する。未定義の状態・所属不明の明細、同名対象、IDと表示の対応も照合する。画面の形式は固定せず、表示から読める関係と元資料が一致するかで判断する。可能なら、元資料を見ない別の担当へ画面だけの読解とAIへの対象指定を依頼し、元資料を持つ担当が照合する。

初版の配信先のケースでは、`q7`・`soft` の意味を創作しない。表示した人向けの意味を元資料と照合する。AIへの指示では、画面だけを見る役が対象と意図を伝え、元資料を持つ役が同名の別対象から一意に特定できるか確認する。

構造、保護対象、レビューの無変更は静的に検査する。代表的な幅、文字拡大、長い値、エラーは利用できる描画環境で確認し、比較と操作を実際に進める。画面を見たAIの代理回答、人による初見理解、実際の読み上げは別々に記録する。未実施は未実施とする。

スキルの形式検査には、利用環境の skill-creator が提供する `quick_validate.py` も使える。形式検査は行動検証の代わりにはならない。

## 実行記録

再実行用の元資料・依頼・判定基準はこのディレクトリに置き、実施結果と環境・限界は `RESULTS.md` に残す。生成HTML、画像、実行ログ、一時的な検証環境はプロジェクト外の作業先に保存する。実行者が使った版からスキルを変えた場合は、その変更範囲と再検証の有無も記録する。
